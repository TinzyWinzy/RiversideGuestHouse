# 4. Product Overview

The Riverside Guest House Digital Operations System is a **mobile-first guest acquisition and booking system**.

The system combines:

1. A public-facing digital experience for discovery and evaluation.
2. Accommodation and pricing presentation.
3. Structured booking enquiry capture.
4. WhatsApp communication.
5. A lightweight management interface.
6. Structured guest and booking records.

The public application is the **guest acquisition layer**.

The management application is the **operational layer**.

WhatsApp remains an important communication channel rather than being replaced.

The fundamental workflow is:

> **Discover → Enquire → Capture → Respond → Book → Manage**

# 5. Problem Statement

Riverside Guest House needs a clear digital presence where prospective guests can:

* Discover the property.
* Understand the accommodation options.
* Understand the facilities.
* See the starting price.
* Understand the location.
* Request accommodation.
* Contact Riverside through WhatsApp.

At the same time, management needs structured records of enquiries and bookings instead of relying entirely on disconnected conversations.

The system therefore needs to connect **digital discovery with actual guest acquisition and booking operations**.

Additionally, management must not miss new enquiries, must not double-book, and must have a reliable operational record that survives beyond WhatsApp threads.

# 8. Accommodation & Pricing Requirements

## ACC-001 — Multiple Accommodation Types

The system must support multiple accommodation types, initially including:

* Ensuite rooms
* Ordinary rooms

**Priority:** MUST

For MVP, "ordinary room" is defined as a room without a private ensuite bathroom. Amenities, capacity, and rate must be configured per accommodation record.

---

## ACC-002 — Accommodation Details

Each accommodation type should support:

* Name
* Description
* Capacity
* Facilities/amenities
* Images
* Active/inactive status
* Configured price
* Currency

**Priority:** MUST

---

## ACC-003 — Starting Price

The public system should display:

> **From US$20/night**

where this is applicable to the configured accommodation offering.

**Priority:** MUST

The system must not invent room rates that have not been configured or confirmed.

The displayed "from" price should be derived from the lowest active configured rate, not hard-coded.

---

## ACC-004 — Long-Stay Discounts

The system should support Riverside's long-stay proposition.

Initially this can be implemented as:

* A long-stay information section.
* A "Long stay?" option in the enquiry form.
* A request for management to provide/confirm the applicable discount.

**Priority:** SHOULD

A sophisticated automated discount engine is not required for MVP.

---

## ACC-005 — Transparent Pricing

The public system should communicate the client's proposition:

> **No hidden fees. What you see is what you pay.**

The system should not silently introduce additional charges.

**Priority:** MUST

---

## ACC-006 — Pricing Inclusions

For MVP, the following must be defined by the client and reflected in the system:

* What the US$20/night rate includes (per room or per person, single or double occupancy).
* Whether breakfast is included.
* Check-in and check-out times.
* Whether extra guests incur additional charges.
* Any refundable or non-refundable deposit expectation.

**Priority:** MUST

Where these are not yet confirmed, the public site must avoid implying inclusions that have not been stated.

---

## ACC-007 — Rate Snapshot

When an enquiry is created and when a booking is confirmed, the system must store the applicable rate at that moment.

Fields to persist:

* `quotedRate`
* `currency`
* `quotedAt`

This prevents later rate changes from silently altering historic records.

**Priority:** MUST

### FR-011 — Booking & Enquiry Status

**Enquiry status:**

```text
NEW
  ↓
CONTACTED
  ↓
PENDING
  ↓
CONFIRMED
  ↓
COMPLETED
```

Cancellation:

```text
NEW → CANCELLED
CONTACTED → CANCELLED
PENDING → CANCELLED
CONFIRMED → CANCELLED
```

**Booking status:**

```text
PENDING
  ↓
CONFIRMED
  ↓
COMPLETED
```

Cancellation and no-show:

```text
PENDING → CANCELLED
CONFIRMED → CANCELLED
CONFIRMED → NO_SHOW
```

The enquiry is the record of the **conversation**. The booking is the record of the **stay**. Only one booking may exist per enquiry.

Unsupported transitions must be rejected server-side.

When a new enquiry is created, management must be notified promptly.

For MVP, this should be:

* An email to a configured management address, and
* Optionally a WhatsApp notification to a configured management number.

A silent dashboard that requires manual checking is not sufficient.

---

### FR-018 — Anti-Spam / Rate Limiting

The public enquiry endpoint must be protected against abuse.

Requirements:

* App Check or equivalent on the public client.
* Rate limiting per IP and per phone number.
* Server-side validation.
* Optional captcha challenge on suspicious submissions.

### FR-019 — Availability Stance

For MVP, the system does **not** maintain live room inventory.

This must be made clear:

* The public site must not imply instant confirmation.
* Enquiries are requests, not reservations.
* Confirmation happens only after management responds.

If automated availability is added later, it must be introduced as a distinct capability.

The system must:

* Publish a privacy policy.

* State retention rules.
* Allow guests to request deletion where feasible.

# 1. Architecture Intent

The system should be a **small, maintainable operational platform**, not a full hotel-management system.

The architecture must support:

* Multiple room types.
* Configurable accommodation.
* Configurable pricing.
* Long-stay enquiries.
* Structured booking requests.
* WhatsApp communication.
* Guest records.
* Management operations.
* Management notifications.
* Future expansion.

The MVP should remain simple enough to build and operate without unnecessary infrastructure.

---

# 2. Proposed Technology Baseline

Recommended baseline:

```text
Frontend Build:      Vite
Frontend Framework:  React + TypeScript
Public Rendering:    Pre-rendered / SSG (see Section 3)
Hosting:             Vercel

Backend Platform:    Firebase
Database:            Cloud Firestore
Authentication:      Firebase Auth (custom claims for roles)
Storage:             Firebase Cloud Storage
Server Logic:        Firebase Cloud Functions
Spam Protection:     Firebase App Check (reCAPTCHA v3)
Notifications:       Firebase Cloud Functions (email + optional WhatsApp)

Maps:                Google Maps
Communication:       WhatsApp (wa.me deep link)
```

The architecture should remain provider-flexible where practical.

---

# 3. SEO & Rendering Strategy (Critical)

A plain Vite SPA is client-rendered and will **not** meet FR-014 reliably.

Chosen approach for MVP:

**Pre-render public routes at build time** using one of:

* `vite-plugin-ssr` / Vike, or
* A prerender plugin such as `vite-plugin-prerender` or `react-snap`, or
* A separate static site generator for public pages, with Vite SPA only for the management dashboard.

Requirements:

* Public routes must produce static HTML at build time with meaningful content.
* Metadata (title, description, Open Graph, canonical) must be present in the pre-rendered HTML.
* `robots.txt` and `sitemap.xml` must be generated at build.
* Structured data (`LodgingBusiness`, `LocalBusiness`) must be included on the Home page.

If pre-rendering is not implemented, the SEO requirement is not met and the MVP should not ship as-is.

# 7. Rate Architecture

Pricing should be **data-driven**.

Rates should not be hard-coded throughout the frontend.

For MVP, a simple nightly rate on each accommodation is sufficient:

```text
accommodations/{id}
  rate: 20
  currency: "USD"
```

The public interface may display:

> **From US$20/night**

provided that the corresponding rate has been configured.

A separate rate collection (seasonal, occupancy-based, long-stay) is deliberately deferred.

MVP should **not** implement a complex discount engine.

Instead:

```text

  ↓

  ↓

  ↓
```

# 10. Booking State Model

**Enquiry:**

```text
   NEW ──► CONTACTED ──► PENDING ──► CONFIRMED ──► COMPLETED

   NEW ─────────────► CANCELLED
   CONTACTED ───────► CANCELLED
   PENDING ─────────► CANCELLED
   CONFIRMED ───────► CANCELLED
```

**Booking:**

```text
   PENDING ──► CONFIRMED ──► COMPLETED

   PENDING ────────────► CANCELLED
   CONFIRMED ──────────► CANCELLED
   CONFIRMED ──────────► NO_SHOW
```

Unsupported transitions must be rejected server-side.

Only one booking may exist per enquiry.

# 11. Database Relationships

```text
settings/property     (single document)

accommodations
   │
   ├──────< enquiries
   └──────< bookings

guests
   │
   ├──────< enquiries
   └──────< bookings

enquiries
   │
   └────── 0..1 bookings

users
   │
   └──────< auditEvents
```

In Firestore, these relationships are represented by document reference fields (e.g. `enquiries/{id}.guestId`, `enquiries/{id}.accommodationId`, `bookings/{id}.enquiryId`).

Composite indexes required:

* `accommodations`: `active == true` (single-field is enough).
* `enquiries`: `status ASC, createdAt DESC`.
* `bookings`: `status ASC, checkIn DESC`.

# 12. API Boundaries

Because this is Firebase, "API" means Cloud Function callable functions and Firestore access governed by security rules.

## Public

```text
Firestore reads:
  GET settings/property
  GET accommodations where active == true

Cloud Functions (callable):
  createEnquiry(payload) → { enquiryId, whatsappUrl }
```

## Management (authenticated, role-gated)

```text
Firestore reads/writes:
  enquiries, bookings, guests, accommodations

Cloud Functions (callable):
  convertEnquiryToBooking(enquiryId, overrides)
  updateEnquiryStatus(enquiryId, nextStatus, notes?)
  updateBookingStatus(bookingId, nextStatus, notes?)
```

## Notifications

```text
Cloud Function triggers:
  onNewEnquiryNotify (Firestore onCreate on enquiries)
```

# 13. Authentication & Authorization

Operational functionality requires authentication.

Minimum MVP roles:

```text
ADMIN
MANAGEMENT
```

Roles are stored as Firebase Auth **custom claims** (`role`) and mirrored in `users/{uid}` for display.

The architecture should allow additional roles later:

```text
STAFF
HOUSEKEEPING
MANAGER
ADMIN
```

Authorization must be enforced at the server/database level via:

* Firestore security rules, and
* Cloud Function checks on callable functions.

UI restrictions alone are insufficient.

# 14. Security

The system must:

* Use HTTPS (Vercel and Firebase provide this by default).
* Validate all submitted data server-side.
* Keep secrets server-side (Firebase Secret Manager / environment config).
* Protect guest information.
* Protect management routes.
* Prevent public access to operational records.
* Use Firestore security rules as the primary database-level access control.
* Use Firebase App Check on the public client.
* Apply rate limiting on `createEnquiry`.
* Record material management changes in `auditEvents`.
* Avoid exposing unnecessary guest information in URLs.
* Establish data retention rules before production.

### Firestore rules summary

```text
settings/property          read: public | write: admin
accommodations             read: public (active only) | write: management+
enquiries                  read/write: management+ | create: denied to public
bookings                   read/write: management+
guests                     read/write: management+
users                      read: self or admin | write: admin
auditEvents                read: admin | write: functions only
```

Public enquiry creation happens only through the `createEnquiry` Cloud Function.

# 16. WhatsApp Integration

The WhatsApp integration provides a bridge between structured system data and human communication.

The `createEnquiry` Cloud Function returns a `whatsappUrl`:

```text
https://wa.me/<managementNumber>?text=<url-encoded-context>
```

Example context:

```text
Hello Riverside Guest House,

I would like to enquire about accommodation.

Ref: ENQ-2026-0001
Name: John Doe
Check-in: 24 September 2026
Check-out: 27 September 2026
Guests: 2
Room: Ensuite
Long stay: No

Please confirm availability and pricing.
```

If WhatsApp is unavailable or the user does not continue to WhatsApp, the enquiry remains stored in Firestore.

Sensitive guest data (email, phone) must not be placed in the URL beyond what the message itself contains.

# 23. Architecture Decisions

| Decision                                          | Reason                                                                |
| ------------------------------------------------- | --------------------------------------------------------------------- |
| Firestore over relational DB                       | Fits Firebase stack; MVP relationships are simple                     |
| Configurable accommodation                        | Riverside has multiple accommodation types                            |
| Rate on accommodation, not a separate collection  | Sufficient for MVP; avoids premature complexity                       |
| Long-stay enquiry rather than discount engine     | Supports the business requirement without unnecessary MVP complexity  |
| WhatsApp as communication layer                   | Preserves the existing human workflow                                 |
| Firestore as operational source of record         | Prevents WhatsApp conversations from being the only record            |
| Cloud Functions for writes                        | Enforces validation, rate limiting, and state transitions server-side |
| Pre-rendered public Vite pages                    | Meets SEO requirement; plain SPA does not                             |
| Single property initially                         | Matches current business scope                                        |
| Public + management surfaces                      | Separates customer acquisition from operations                        |
| App Check + rate limiting                         | Protects the public enquiry endpoint                                  |
| Email notification on new enquiry                 | Prevents missed enquiries                                             |
